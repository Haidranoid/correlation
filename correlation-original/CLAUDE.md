# Claude Code Configuration for Ruby on Rails Project

## Problem-Solving Workflow
- Before generating code, **analyze the request and outline the steps to solve the problem**.
- Think step-by-step, and explain assumptions or unknowns.
- Only generate final code after confirming the problem is understood.
- Use comments like `# Step 1`, `# Step 2` if outlining inside the code itself.
- If in doubt lookup more information on the web.

## Project Context
This project is a Ruby on Rails application hosted in a Git repository. It includes:
- A PostgreSQL
- RSpec tests
- Background jobs using Sidekiq
- API endpoints via controllers and serializers
- A frontend with ERB or Hotwire/Turbo (optional)

## Your Goals
1. Help improve and refactor the Ruby and Rails codebase.
2. Write clean, idiomatic, well-documented Rails code.
3. Ensure compatibility with the current Rails version (specify if known, e.g. `Rails 7.1`).
4. Suggest or make improvements in performance, test coverage, and maintainability.

## Coding Guidelines
- Follow community best practices from [rubocop](https://github.com/rubocop/rubocop), Rails style guides, and [fast-ruby](https://github.com/JuanitoFatas/fast-ruby).
- Prefer strong parameters and scopes over manual filtering.
- Avoid N+1 queries; suggest `includes`, `joins`, or `preload` where needed.
- Use background jobs for slow or async operations.
- Use partials or components for repeated view logic.
- Minimize controller complexity by moving logic into models or service objects.

## Collaboration Preferences
- When refactoring, explain reasoning briefly in comments or commit messages.
- If a file is part of a Git repo, preserve Git history when possible.
- If unsure about a change, comment with `# CLAUDE: unsure — needs human review`.

## Rails-Specific Hints
- Prefer `find_each` over `each` for large record batches.
- Use `ActiveModel::Serializer` or `json.jbuilder` to render APIs.
- Write tests for edge cases and regressions in `spec/` or `test/` directories.
- In migrations, use reversible syntax and `safe` operations for production environments.

## What to Avoid
- Don’t generate scaffolds unless explicitly asked.
- Don’t overwrite files outside `app/`, `config/`, `lib/`, or `db/` unless prompted.
- Don’t generate full test or spec boilerplate unless there's none to start from.
- Don’t suggest JavaScript unless the frontend depends on it.
- Don't generate custom code if a gem already exists to solve the problem.  Use the gem if possible.

## Output Preferences
- Prefer inline edits to entire file rewrites.
- If generating new files, show full path and filename (e.g., `app/services/user_creator.rb`)
- Label changes clearly if editing multiple files in one response.

## Example Tasks You Can Help With
- “Refactor this service object to reduce complexity.”
- “Suggest database indexes for this query-heavy model.”
- “Add a background job for this controller action.”
- “Fix failing specs in this diff.”
- “Optimize this SQL generated by ActiveRecord.”

## Code Validation
- After any changes, **validate that the code will still work**.
- Check for syntax errors, missing dependencies, or incorrect method calls.
- Confirm that any renamed variables or refactored methods are updated consistently.
- If test files are present (e.g., in `spec/` or `test/`), suggest tests or note affected ones.
- Add a comment if any area needs manual verification: `# CLAUDE: check this logic during testing`

## Git Commit Behavior
- After completing and validating a change, suggest a **clear, conventional commit message**.
- Follow this format: `feat:`, `fix:`, `refactor:`, or `test:` where appropriate.
- Example: `refactor: extract user lookup to service object`
- Summarize what changed and why in one sentence.
- Only suggest a commit after the code is validated and safe.
- If multiple changes are made, group commits logically (e.g., “Add background job for notification sending”).
- After asking for permission do the commit.

## Rspec Preferences
- Do not create new specs or run them unless specifically asked to do so.  They will probably change frequently and take too long.
